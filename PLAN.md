## Phase 5 — Extraction Provider Evaluation (Spike) ✅

Run 18 representative synthetic invoices through a real extraction provider, evaluated against authoritative ground truth, with business-critical fields (invoice number, invoice date, due date, currency, subtotal, tax, total) reported separately from the aggregate score. Produces a written, evidence-based provider decision.
**Depends on:** nothing from Phases 2–4 — ran in parallel with them.

**Built:** the full harness (`spike/schema.py`, `spike/providers/{azure,mistral,claude}_provider.py`, `spike/pricing.py`, `spike/run_spike.py`, `spike/evaluate.py`, `spike/README.md`), the approved 18-document synthetic dataset with ground truth generated first and authoritative by construction (`spike/invoice_specs.py`, `spike/render.py`, `spike/formatting.py`, `spike/degrade.py`, `spike/generate_samples.py`), and a full test suite (`spike/test_{formatting,providers,evaluate,dataset_integrity,run_spike,provider_readiness}.py` — 68 tests without `[spike]` installed, 75 with it). Two currency-rounding/layout bugs were caught by actually rendering and inspecting output, not just confirming generation succeeded. Two real Mistral SDK bugs (wrong import path, wrong JSON-schema field name) were caught by static package introspection before spending anything, and are now permanently guarded by `spike/test_provider_readiness.py`.

**Real run: Mistral OCR only, once, against all 18 documents.** Not a Mistral-vs-Claude comparison as originally planned — Azure was excluded from the start (project owner scope decision, optional not required), and Claude was excluded from the real run because the Anthropic credential in this environment was exposed during diagnosis and is treated as compromised; no call was made with it. Result: 18/18 processed (one transient `404` on `inv_04`, resolved with a single targeted retry of that one document, not a full rerun), **98% overall field accuracy, 98% business-critical-field accuracy**, $0.076 total cost. Three named critical-field errors (currency on the deliberately-ambiguous `inv_11`; a hallucinated due-date and a transposed invoice-date, both on `inv_13`) and one empirically-confirmed limitation (Mistral's structured-output call returns no per-field confidence at all) are recorded with full detail in `docs/extraction-strategy.md`, "Real results," and `spike/report.md`.

**Decision:** Mistral OCR is the Phase 6 `ExtractionProvider` — see `docs/adr/0006-extraction-provider.md` for the decision, its evidence, and its explicitly-stated confidence caveat (single-provider validation, not comparative). The confidence-score gap changes Phase 6/7's review-routing design: it must route via deterministic validation failures and targeted plausibility checks, not a per-field confidence threshold table, for this provider.

**Two credential-exposure incidents occurred during diagnosis before this final run** (an `env | grep` matching a variable name and printing its value; a raw SDK exception traceback echoing a credential embedded in a malformed header). Both keys were rotated by the project owner as a result. `docs/security.md` gained a "Secret-safe debugging practice" section recording exactly what went wrong and the rules it produced, so this isn't repeated in later phases.

**Completion criteria:** met.

## Phase 7 — Deterministic Validation ✅

Required-field checks and arithmetic consistency, independent of confidence.
**Depends on:** Phase 6's normalized fields.
**Built:** `app/validation.py` — `check_required_fields()` (one rule per field: vendor_name, invoice_number, invoice_date, currency, subtotal, tax, total; `due_date` deliberately excluded — the real Phase 5 run confirmed a missing due date is a legitimate value, not an extraction failure) and `check_arithmetic_consistency()` (subtotal + tax = total within a $0.02 tolerance, with its own distinct reason when a component is missing entirely vs. when the numbers just don't add up). Wired into `app/routers/documents.py`: `EXTRACTED` → `VALIDATING` → `VALIDATED` (all rules passed) or `NEEDS_REVIEW` (any failed) — synchronous, same request, same reasoning as Phase 6 (no worker until Phase 13). Every rule's individual result is persisted to `validation_results`, not just a summary reason on `state_history`.
**Verified, not assumed:** 10 pure-logic tests in `tests/test_validation.py` — every rule has both a passing and a failing case with a specific reason string, including the exact adversarial cases PLAN.md named up front (a total off by one cent beyond tolerance, a missing invoice number), plus multi-failure and missing-component cases. 6 new/updated integration tests in `tests/test_documents_api.py` confirm the wiring end to end: a valid upload reaches `VALIDATED` with the correct 5-state history sequence; a missing required field or an arithmetic mismatch reaches `NEEDS_REVIEW` with the specific `validation_results` row to prove it; a missing `due_date` alone does *not* trigger review. 90 tests pass total (97 with `[spike]` installed). Docker image rebuilt and confirmed to build, migrate, and serve `/health` correctly.
**Completion criteria:** met — every rule has a passing and a failing test case with a correct, specific reason string.

## Phase 8 — Vendor Matching ✅

Deterministic fuzzy matching of extracted vendor names against a known-vendor table.
**Depends on:** Phase 6's normalized vendor field.
**Built:** `app/vendor_matching.py` — `normalize_vendor_name()` (lowercase, strip punctuation, matching the `Vendor.normalized_name` column's own convention), `find_best_match()` (pure function over plain `(id, name)` tuples, not ORM objects, so it's fully Tier-1 testable — uses `rapidfuzz`'s similarity scoring, threshold 85/100), and `check_vendor_known()` (wraps a match into the same `RuleResult` shape Phase 7's rules use). `app/seed_vendors.py` seeds 18 realistic vendor names mirroring the Phase 5 spike dataset (copied as plain strings, never imported from `spike/` — the app must never depend on the throwaway evaluation package), idempotent, run manually via `python -m app.seed_vendors` (not on every app startup, same reasoning as manual migrations). Wired into `app/routers/documents.py`'s existing `_run_validation_step` — vendor matching is folded into the same `VALIDATING` step as Phase 7's rules and feeds the same `VALIDATED`/`NEEDS_REVIEW` decision, since `docs/workflow.md` lists it as a conceptual step but the state machine has no dedicated "matching" state.
**Verified, not assumed:** 10 pure-logic tests in `tests/test_vendor_matching.py` (exact match, near-miss spelling still matches, genuinely unknown vendor correctly flagged, no-vendors-on-file, missing-name — per PLAN.md's stated completion criteria). 2 new integration tests confirm the wiring: an unrecognized vendor reaches `NEEDS_REVIEW` with a named `vendor:known` validation_results row; a cosmetic spelling variation ("Acme Corp." vs. "Acme Corp") still reaches `VALIDATED`. All existing Phase 6/7 happy-path tests updated to seed a matching vendor first, since a document's vendor now has to actually be recognized to sail through untouched — this is more realistic than before, not a workaround. 102 tests pass. Docker image rebuilt; the seed script was run twice against a real Postgres to confirm both that it works and that it's genuinely idempotent (18 inserted, then 0 inserted / 18 already present).
**Completion criteria:** met — a known vendor with a typo still matches; a genuinely new vendor is correctly flagged, not silently created.

## Phase 9 — Duplicate Detection ✅

Content-hash and fuzzy matching to catch the same invoice arriving through a different request.
**Depends on:** Phase 7's validated fields; Phase 4's file hashing.
**Built:** `app/duplicate_detection.py` — `find_exact_hash_duplicate()` (identical file bytes, pure function over plain `(id, hash)` tuples) and `find_content_duplicate()` (exact-after-normalization match on vendor + invoice number + total + invoice date together, not independent fuzzy scoring — a partial match is two different invoices, not a duplicate). Wired into `app/routers/documents.py` at two distinct points: the exact-hash check runs right after `RECEIVED`, *before* extraction, so a re-upload of the same bytes never spends a paid extraction call; the content-level check runs first inside `_run_validation_step`, short-circuiting the other Phase 7/8 rules for a document about to be discarded anyway.
**A real design discrepancy was found and fixed, not glossed over:** Phase 9's own completion criteria ("without re-running extraction... on it") requires skipping extraction entirely for an exact-hash duplicate, but the original `docs/state-machine.md` diagram only documented `VALIDATING → DUPLICATE`. Added `RECEIVED → DUPLICATE` as a documented, reasoned addition (see that file) rather than silently building code that contradicted the written design.
**Verified, not assumed:** 13 pure-logic tests in `tests/test_duplicate_detection.py`, including PLAN.md's named cases (identical file twice, same invoice re-typed with a formatting difference, two genuinely different same-vendor same-day invoices correctly NOT flagged) plus tolerance and missing-field edge cases. 3 new integration tests — critically, one proves via a call-log on the fake provider that an exact-hash duplicate's `extract()` is never invoked at all (not just that the end state is right), one confirms a content-level duplicate across genuinely different file bytes, one confirms two different invoices from the same vendor are correctly NOT merged. 118 tests pass. Docker image rebuilt and confirmed to build, migrate, and serve `/health`.
**Completion criteria:** met — a resubmitted invoice reaches `DUPLICATE` without re-running extraction or validation on it.

## Phase 10 — Human Review Workflow ✅

Review queue, side-by-side document/field UI, correction capture as an audit event.
**Depends on:** Phases 7–9 (all review triggers must exist).
**Built:** `app/review.py` — pure `parse_corrected_value()` parsing each correction's raw string into the type its target `ExtractionResult` column needs (numeric, date, or plain string), raising `UnknownFieldError`/`InvalidFieldValueError` rather than silently coercing bad input. `app/routers/review.py` — `GET /review` (the queue, oldest first, each item with its specific failed `validation_results` rows, not just a summary), `GET /review/{id}` (fields, failed rules, a signed file URL), `POST /review/{id}/correct` (writes one `review_events` row per field with the original value captured before the overwrite, applies the correction to `extraction_results`, and moves `NEEDS_REVIEW → VALIDATED` directly — per `docs/state-machine.md`, a correction is the reviewer's own assertion the value is right, so it does not re-run Phase 7/8's rules), `POST /review/{id}/reject` (`NEEDS_REVIEW → REJECTED`, reviewer + reason recorded in `state_history`). Also completed a promise made in Phase 4's code: `StorageProvider.sign_url()` was a stubbed `NotImplementedError` with a comment saying "implemented starting Phase 10" — now a real HMAC-SHA256 signed URL (`app/storage.py`), served by a new, deliberately unauthenticated `app/routers/files.py` (`GET /files/{storage_path}`) — the signature and its expiry are themselves the authorization, exactly as `docs/security.md`'s "signed, short-lived storage URLs" control describes, so the link can be dropped straight into a reviewer's browser without the bearer token every other route requires.
**A real bug was found and fixed via the test suite, not assumed away:** the first version of `_failed_rules()` queried `validation_results` by document ID alone, so a document that had just been corrected (and moved to `VALIDATED`) still showed its old, now-resolved failed rule in the response — `validation_results` is intentionally never updated or deleted (same append-only rationale as `state_history`), so "currently failing" has to be computed as "failing AND still `NEEDS_REVIEW`," not just "has a failed row somewhere in history." Fixed by gating `_failed_rules()` on the document's current state.
**Verified, not assumed:** 9 new Tier 1 tests (`tests/test_review.py` for correction parsing, `tests/test_storage_signing.py` for the HMAC signing/verification primitives — wrong secret, tampered path, tampered expiry, expired-but-correctly-signed). 15 new integration tests (`tests/test_review_api.py`) covering the queue's contents and exclusions, detail 404, a full correct-then-VALIDATED round trip with `review_events` and `state_history` assertions, unknown-field and unparseable-value 422s, already-resolved 409s, reject-with-attribution, auth requirements on every `/review` route, and the signed file URL actually serving the original bytes with no `Authorization` header at all plus rejecting a tampered or expired one. 146 tests pass, lint clean. Docker image rebuilt, migrated, health-checked, and smoke-tested live against the real running container (`GET /review` with a real bearer token, not just the test client).
**Completion criteria:** met — a `NEEDS_REVIEW` document can be listed with its specific failure reasons, viewed side by side with its original file via a signed URL, corrected (writing an auditable `review_events` trail) to reach `VALIDATED`, or rejected to reach `REJECTED`.

## Phase 13 — Reliability & Recovery ✅

Retry/backoff, dead-letter handling, crash/restart recovery for every failure mode in `docs/reliability.md`.
**Depends on:** all prior phases.
**Built:** `app/retry.py` — pure `call_with_retry()`, bounded exponential backoff with an injectable `sleep` for zero-wall-clock-delay tests. Wired around the two real external-provider calls (`_attempt_extraction`'s `provider.extract()`, `_attempt_action`'s `accounting.create_payable()`, both in their respective routers) and, via `app/accounting.py`'s new `notify_with_retry()`, around every notification call — covering `docs/reliability.md`'s provider-timeout/rate-limit and notification-failure rows directly. `app/worker.py` — the scheduled worker from `docs/adr/0003-worker-model.md`, finally built: `find_stuck_documents()` finds anything in `EXTRACTING`/`VALIDATING`/`ACTIONED` past `WORKER_STUCK_TIMEOUT_SECONDS`, `recover_document()` resumes it by calling the exact same internal step functions the synchronous request path uses. `Document.retry_count` (new column + migration) bounds worker-level resumption separately from each call's own in-request retry attempts, so a sustained outage dead-letters (`FAILED` + alert) instead of the worker looping forever.
**A real refactor, not just new code, was required and done carefully:** `_run_extraction`/`_run_validation_step` (documents.py) and the inline body of `action_document` (actions.py) were each split into a `_begin_*` (the state transition, upload-request-only) and `_attempt_*` (the actual work, callable standalone) pair — this is what lets the worker resume a document already sitting in `EXTRACTING`/`VALIDATING`/`ACTIONED` without re-recording or mis-recording a transition into a state it's already in. Existing Phase 4/6/7/8/9/12 endpoint contracts were preserved exactly — no test from any earlier phase needed to change except a `LocalStorageProvider` constructor-shape update that predates this phase.
**Two things were found and fixed, not shipped broken:** (1) the route's own accounting-write-failure `502` response was accidentally dropped during the actions.py refactor — caught by rerunning Phase 12's own tests, not a new test, which is exactly why "no existing test may regress" matters; fixed by having `_attempt_action` return `(succeeded, notification_sent)` instead of a single ambiguous bool. (2) the autogenerated `retry_count` migration added a `NOT NULL` column with no default, which would break on any existing row — added `server_default='0'` by hand before applying it, not accepted as-is.
**Verified, not assumed:** 5 new Tier 1 tests for `call_with_retry()` (first-attempt success, success-after-failures with exact backoff-sequence assertions, exhaustion, single-attempt-never-sleeps). 12 new tests for the worker — `find_stuck_documents()`'s timeout/state filtering, and `recover_document()` exercised directly against a hand-inserted stuck row for all three in-flight states (success and persistent-failure for `EXTRACTING`/`ACTIONED`, a `VALIDATING` case that proves via an exploding fake provider that recovery never re-touches extraction), the retry-cap dead-lettering short-circuit, and `run_once()` recovering multiple documents in one pass while isolating one document's unexpected exception from the others. All existing Phase 4-12 tests re-run unmodified in behavior and still pass. 187 tests pass, lint clean. Two real autogenerated Alembic migrations reviewed (not blindly accepted) and applied from empty. Docker image rebuilt, migrated, health-checked, and `app.worker.run_once()` smoke-tested live against the running container.
**Completion criteria:** met — every technical failure mode in `docs/reliability.md` that doesn't require a real external outage to observe now has bounded retry-with-backoff, and a document stuck in an in-flight state after a simulated crash (a stuck row written directly to the database, per `docs/testing-strategy.md`) is recovered by the worker without being reprocessed from `RECEIVED`.

## Phase 14 — Security Hardening ✅

Implements and verifies every control in `docs/security.md`.
**Depends on:** Phases 4, 6, 10, 11.
**Built:** Most of `docs/security.md`'s controls were already implemented as each owning phase landed (upload validation Phase 4, signed URLs Phase 10, idempotency Phase 4/9, attribution fields Phase 10/11) — this phase's job was consolidated verification plus closing the specific gaps that only show up under a dedicated security pass. `.gitleaksignore` — one precise, fingerprinted suppression for a verified false positive, not a blanket rule disable. `tests/test_security_hardening.py` — the prompt-injection adversarial fixture `docs/testing-strategy.md` named as Phase 14's own, attribution-required tests for all four review/approval mutation endpoints, and a regression guard asserting no bank/IBAN/routing field ever becomes extractable or correctable. A new "Data handling" section in `README.md` disclosing Mistral's actual free-tier training policy (looked up fresh, not assumed) and why it's an acceptable risk here (every document processed is synthetic).
**A real security bug was found and fixed, not just verified:** `_attempt_extraction`/`_attempt_action` (Phase 13) formatted a failed provider call's raw exception message into the `state_history` reason and the alert notification — `f"{type(exc.last_error).__name__}: {exc.last_error}"` — which is exactly the pattern `docs/security.md`'s "Secret-safe debugging practice" section exists to prevent, having already caused a real key leak once in this project (Phase 5's `httpcore` transport error echoing back an `Authorization` header). The comment directly above that line even said the right thing ("never raw provider request/response content") while the code beneath it did the opposite. Fixed in both call sites (and `app/accounting.py`'s `notify_with_retry`, defensively, for when a real SMTP/accounting adapter eventually becomes credentialed) to log the exception type only.

## On changing this structure

This 19-phase structure was deliberately designed around concept boundaries, not an arbitrary count, and has been approved. It should not be redesigned, merged, split, or reordered mid-project on aesthetic grounds. The one legitimate reason to revise it: a concrete implementation contradiction is discovered — e.g. two "separate" phases turn out to be impossible to build independently, or a phase turns out to secretly contain two unrelated concepts. If that happens, the specific contradiction should be stated plainly before any structural change is made.
